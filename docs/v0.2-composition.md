# Composed-world foundation — v0.2.0

Composition combines at most eight local World IR documents into one schema `1.1` world.
Each service owns qualified resource tables and actions such as `payments.payment`,
`payments.create_refund`, and `email.message`. Namespace names are lowercase letters, digits,
and underscores, beginning with a letter, at most 32 characters. Action/resource collisions
are rejected. Source provenance and compatibility issues are retained.

```bash
worldforge import examples/payments/openapi.yaml --workspace .worldforge/payments-source
worldforge import examples/email/tools.json --format mcp --workspace .worldforge/email-source
worldforge world compose --service payments=.worldforge/payments-source/world.json --service email=.worldforge/email-source/world.json --link email.message.customer_id=payments.customer --world-id payments-email --workspace .worldforge/composed
worldforge world inspect --workspace .worldforge/composed
worldforge scenario generate --namespace payments --count 2 --seed 42 --workspace .worldforge/composed
worldforge run --workspace .worldforge/composed
```

The email fixture supports creating/getting/listing local message records; it never sends email.
The explicit cross-service link validates `email.message.customer_id` against the existing
`payments.customer` table. Relationships are not inferred from similar field names. Referenced
resources/fields must exist and use compatible string identifiers. Conflicting schema annotations
or duplicate relationships fail compilation.

Composition remaps resource references in schema positions, action bindings, source relationships,
and scenario action/fault references. Literal example/default data is not rewritten as a schema.
Each refund service must independently declare all refund rules; another service cannot lend
missing rules to an invalid refund action.

`compose_scenario` binds a source payments scenario to its selected service/world version, sets
visible `payments_namespace`, and allocates empty tables for the other services. The reference
agent and evaluator select the qualified payment/refund resources. The CLI workflow above runs
the payments task while the email tables remain available as composition evidence; it does not
claim that the narrow reference policy performs an email workflow.

Library callers may provide explicit initial `extra_state` belonging to other namespaces. It
must use qualified resource names, start at step zero, and cannot overwrite the payments source
state. Authors can explicitly add other declared actions to a scenario and write a corresponding
trusted agent. The integration fixture exercises the shared boundary; the evaluator's supported
objective remains refunding the duplicate payment, with protected unrelated records preserved.

There is one in-process state owner, logical step clock, failure schedule, ordered event stream,
runtime budget, and run artifact. Independent runs never share mutable tables. This is a
multi-service architecture foundation, not distributed transactions, networking, queues,
asynchronous message delivery, a broad service catalog, or complete Payments+Email+GitHub+Slack
behavior. Out-of-order event simulation and further services are deferred.
