# v0.2 security and replay boundaries

WorldForge's built-in compilation, simulation, search, and reference provider workflows are
local synthetic execution. They do not contact OpenAPI server URLs, MCP servers, production
payment APIs, or model providers. Trusted custom agent/provider implementations run with the
host process's permissions and may independently access those systems. WorldForge is not an
in-process sandbox and does not promise production fidelity.

## Untrusted declarations and observations

OpenAPI/static MCP inputs use safe bounded JSON/YAML parsing. Duplicate keys, aliases/tags,
nonfinite values, recursion, remote/dynamic references, unsupported dialect mechanisms, and regex
schema constraints are rejected. Reference expansion, schema trees, and compiled output have
separate limits. Direct World IR inputs are also validated through the simulator's offline schema
boundary. No schema reference fetches network content or executes a script.

The direct simulator schema boundary caps depth at 64, combined resource/input/response schema
nodes at 200,000, and cumulative schema keys/strings at 4 MiB before recursive validation.
This remains a subset restriction, not a general JSON Schema execution sandbox.

MCP names/descriptions/metadata and synthetic tool results are data, including when they contain
malicious instructions. Compilation does not follow descriptions, infer hidden business rules,
or grant a tool production access. A connected agent must treat synthetic text as untrusted;
WorldForge does not claim a general prompt-injection filter or immunity for a model.

Workspace paths are explicitly supplied by the operator. Run/certificate IDs have fixed formats
and are never treated as paths. Stores validate regular files and sizes; certificate files and
their immediate store directory reject symlinks, and saving does not overwrite existing IDs.
The workspace is a trusted local boundary, not protection against an attacker controlling the
host filesystem or racing parent-directory changes.

## Budgets and executable adapters

Scenarios bound steps, virtual latency, and cooperative runtime. Search specs separately bound
seeds/conditions, candidates, total executions, verification attempts, and elapsed search time.
Runtime validates typed decisions and bounds observable metadata/provider records. Resource
warnings expose repeated calls and nearing step budgets. These safeguards limit the built-in
simulation path; they do not guarantee interruption of hostile synchronous Python, prevent
arbitrary subprocesses, or enforce billing limits inside independently written adapters.

Run `1.1` admission bounds the combined world/scenario context at 8 MiB, state at 4 MiB,
world/scenario identifiers at 256 UTF-8 bytes, and the world version at 128 bytes. The retained
trace is limited to 16 MiB, with 4 MiB reserved for termination and reporting. Byte accounting
conservatively includes pretty-printed artifact indentation. Provider receipts additionally
have a 1 MiB aggregate byte budget and a 2,000-record limit. Modern replay enforces the same
admission and trace rules; historical run `1.0` retains its original policy.

`TRACE_BUDGET_EXHAUSTED` records the rejected phase and byte measurements, and the run terminates
with `artifact_limit`. Tool transitions are staged on an isolated simulator state and admitted
together with their complete event batch. A rejected transition does not mutate the retained
world or advance its action counters. A rejected decision remains observable in the termination
event, including reported provider usage; it is never executed. Oversized initial context is
rejected before agent callbacks. These limits bound retained artifacts, rather than providing
operating-system memory isolation for trusted Python code.

Custom Python factories require explicit `--trust-agent-code` and execute during import/factory
creation. Loading/inspecting a Failure Certificate never executes a stored Python path.
Reproduction defaults only to approved built-in selectors; a custom reproduction adapter must
be selected explicitly with the trust flag. Use external process/container/network/filesystem
controls for code you do not trust. No optional real-provider implementation ships in core.

## Artifact privacy and integrity

Run and certificate artifacts may embed tasks, observations, action arguments/results, provider
identity/usage, world/scenario state, metadata, errors, and file-source provenance. They may
contain private data if supplied by an operator or custom adapter. Automatic PII/secret scrubbing,
encrypted storage, telemetry upload, and credential management are not implemented. Examples
use synthetic data; review and sanitize artifacts before sharing.

The certificate world hash verifies consistency of the embedded World IR. Strict replay checks
event ordering/context, recorded transitions/results, evaluation, and deterministic resource
values. Neither is a signed attestation, authorship proof, or claim of tamper-proof storage.
Preserved actual elapsed time is checked as recorded metadata, not reproduced performance.

Legacy run `1.0` retains historical replay/evaluation semantics; run `1.1` checks richer events
and unsafe key-change attempts. External model responses are recorded observations. Fresh external
inference can differ and must never be described as deterministic merely because the simulator
replays its recorded tool actions. Certificate verification rates describe completed observed
trials, not confidence in future production behavior.

The current scope excludes live MCP execution, real telemetry/HAR/log ingestion, production API
execution, automatic training/self-modification, and cloud hosting. Report vulnerabilities using
[the repository security policy](../SECURITY.md).
