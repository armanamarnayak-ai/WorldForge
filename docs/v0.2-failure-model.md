# Deterministic failure model — v0.2 development

Legacy scenario `1.0` keeps the original `FailureInjection` shape for `error_before` and
`response_lost`. Richer scenarios use `schema_version: "1.1"` and versioned `FailureSpec` entries:

```json
{
  "schema_version": "1.1",
  "action": "create_refund",
  "kind": "response_lost",
  "occurrence": 1,
  "latency_ms": 0
}
```

The action is an exact World IR action key, including a namespace in a composed world.
`occurrence` selects an eligible valid simulator invocation, not a wall-clock deadline or a
random chance. Invalid arguments, rejected transitions, and disallowed actions do not consume
a fault occurrence. Every attempted allowed simulator action still advances the logical step.
The scenario seed determines generated initial state; the selected fault schedule is explicit.

| Kind | Synthetic behavior |
| --- | --- |
| `error_before` | Return `503` before committing the proposed effect. |
| `response_lost` | Commit the valid effect, then return `504` instead of its response. |
| `delay` | Advance the virtual latency clock and return the normal result. No real sleep. |
| `timeout` | Return `504` before committing an effect; optionally charge virtual latency. |
| `permission_denied` | Return `403` before committing an effect for this occurrence. |
| `rate_limit` | Return `429` before committing an effect; no invented real quota. |
| `service_unavailable` | Return `503` before committing an effect. |
| `malformed_response` | Commit the valid transition and expose `data: null` with an explicit corruption error. |
| `stale_read` | A `get`/`list` reads the run's initial snapshot while current state is preserved. |
| `duplicate_delivery` | Attempt the same action twice, validating the extra transition and recording its outcome. |

Each fault's `latency_ms` is virtual elapsed time, from zero to 60,000 ms. It can accompany
an effect fault. A scenario contains at most 32 conditions, and an occurrence ranges from
1 to 1,000. One `delay` plus one effect fault may target the same action/occurrence; duplicate
conditions or conflicting effect faults are rejected. `stale_read` on a mutation is rejected.

Scenario `1.1` adds `simulated_latency_budget_ms` (default 300,000, maximum 3,600,000) and
`max_runtime_seconds` (default 30, maximum 3,600), alongside the existing `max_steps`
(default 12, maximum 1,000). A virtual-latency overrun saturates the clock at its budget and
returns `504` before an effect. Runtime and callback deadlines bound cooperative async agents;
trusted blocking Python still requires external isolation.

## Honest mutation semantics

Faults are applied around validated transactions. Lost or corrupted responses never authorize
invalid state. Refunds still enforce the declared rules, payment balance, and idempotency key.
Duplicate delivery of a refund with the same key returns the original refund without adding
another ledger entry. A generic create without a fixed identifier can honestly produce a second
valid resource; a rejected second effect is recorded without committing invalid state.

The reference adversary changes its key after a successful refund response is lost. A second
full refund then receives `409`; the evaluator flags the observable unsafe key change. This
is an attempted unsafe retry, not a manufactured double-refund bug.

`FAILURE_INJECTED` events record the selected condition and diagnostic outcomes, and
`SIMULATED_LATENCY` events record clock deltas. These become replay inputs/checks alongside
actions/results/state. Identical world version, scenario, seed, fault schedule, and recorded
actions reproduce the deterministic simulation. Actual runtime latency and fresh external
model inference need not repeat.

Persistent ACL changes, out-of-order asynchronous event delivery, arbitrary wire corruption,
random chaos, and production service failures are not modeled by this subset.
